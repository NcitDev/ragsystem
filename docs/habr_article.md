# Почему ИИ-агенты «слепнут» в больших проектах (и как мы вернули им зрение с помощью RAG)

<img src="https://habrastorage.org/webt/xx/xx/xx/placeholder.png" alt="RAG Architecture" />

Если вы хоть раз просили современного ИИ-агента (будь то Claude, Cursor или кастомный скрипт на базе GPT-4) найти причину бага в большом проекте, то наверняка видели эту печальную картину. Агент бодро пишет `grep "push notification"`, получает простыню из сотен совпадений и начинает маниакально, файл за файлом, читать код. Спустя 38 ходов и десятки тысяч сожжённых токенов он либо галлюцинирует, либо забывает изначальную задачу.

Эту статью я решил поделить на два уровня, вдохновившись [отличным текстом](https://habr.com/ru/companies/selectel/articles/1044854/) про эмбеддинги и гроккинг.

**Первая часть** — базовая механика: почему привычные методы поиска ломают агентам мозг, и как AST-парсинг вместе с эмбеддингами спасают ситуацию.

**Вторая часть** — для тех, кому интересно копнуть поглубже: бенчмарк на 10 реальных сценариях из Signal-Android, разбор алгоритма Two-Phase Blast Radius, честный список минусов RAG (да, индексация Signal заняла у меня ~5 часов) и история того, как я итеративно доводил систему до ума.

## Зачем это всё: цель и миссия

Сразу обозначу рамку, чтобы не было завышенных ожиданий. Миссия проекта узкая и намеренно скучная: **сделать так, чтобы ИИ-агент ориентировался в большом проекте так же хорошо, как он уже умеет писать отдельные функции.**

Это **не** «чат с документацией» и не универсальная база знаний. Единственная цель — убить самый глупый и дорогой режим отказа кодинг-агентов: брутфорс репозитория через `grep` + «прочитать файл и помолиться», пока контекстное окно не забьётся мусором, а агент не забудет задачу.

Из этой цели выпали три принципа:

- **Local-first.** Код не покидает вашу машину. Эмбеддинги, векторная база и (опционально) LLM-планировщик работают локально.
- **Без вендор-лока.** В конфиге выбираете `gemini`, `gpt-4o`, `claude` или полностью локальный `qwen3` через Ollama.
- **Ноль накладных расходов в рантайме.** Языковые серверы (LSP) работают *только* во время индексации; в момент запроса вся структурная информация уже вшита в индекс.

## Часть 1. Для тех, кто устал смотреть, как ИИ читает случайные файлы

### Проблема слепого котёнка в библиотеке

Представьте, что вы отправили очень умного, но слеповатого помощника в Ленинскую библиотеку найти все упоминания «обработки push-уведомлений». Он берёт лупу (`grep`), находит сотни книг со словом «push» и начинает читать их от корки до корки.

В реальной разработке, например в Signal-Android (300K+ строк Kotlin), программист тратит до 40% времени на навигацию: «Где этот класс?», «Кто вызывает эту функцию?», «Что сломается, если я переименую этот интерфейс?». Агенты пытаются делать то же самое, но их контекстное окно (даже 200К токенов) быстро забивается мусором.

Обычные подходы ИИ-поиска:
1. **Грубый grep** — находит сотни совпадений, 90% из которых — комментарии или тесты.
2. **Чтение наугад** — метод проб и ошибок, который стоит вам времени и денег API.
3. **Контекст из IDE** — агент видит только открытый файл, теряя глобальную картину.

### Векторы и деревья (или как нарезать код)

Просто порезать текст на куски по 500 символов — плохая идея. Код имеет структуру.

Здесь на сцену выходит **Tree-sitter** — он строит абстрактные синтаксические деревья (AST). Вместо глупой нарезки текста мы режем код по смыслу на 3 уровня:
- **T1:** файл целиком (общий контекст);
- **T2:** класс или модуль (структурные элементы);
- **T3:** конкретная функция или метод (детали реализации).

Каждый чанк превращаем в **эмбеддинг** — вектор в многомерном пространстве. Мы используем Ollama (Qwen3-Embedding), чтобы перевести смысл кода в массив чисел, и складываем это в векторную базу Qdrant. Теперь запрос "push notification handler" находит не файлы со словом "push", а куски кода, которые *по смыслу* отвечают за обработку уведомлений.

### RAG-демон: архитектура

Чтобы всё работало быстро, мы выделили систему в автономного headless-демона.

```text
┌─────────────────────────────────────────────────────────┐
│                    RAG Daemon (FastAPI)                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │  Qdrant  │  │ Tree-    │  │ Agno     │  │  LSP   │ │
│  │ (vector) │  │ sitter   │  │ Agent    │  │ Server │ │
│  └──────────┘  └──────────┘  └──────────┘  └────────┘ │
│                      :7890                               │
└─────────────────────────────────────────────────────────┘
         │              │              │
    ┌────┴────┐   ┌─────┴─────┐  ┌────┴────┐
    │   CLI   │   │    TUI    │  │AI Agent │
    │ (typer) │   │ (textual) │  │(Claude, │
    └─────────┘   └───────────┘  │ Codex)  │
                                 └─────────┘
```

Демон — единственный процесс, который живёт в фоне, держит модели в памяти, следит за изменениями файлов и мгновенно отвечает на запросы. Клиенты (консоль, GUI, сам ИИ-агент) — тонкие HTTP-обёртки. Упал клиент? Демону всё равно.

LSP-серверы используются *только* во время индексации, чтобы вытащить связи и типы. В рантайме их нет — zero overhead.

## Часть 2. Для тех, кто хочет копнуть поглубже (метрики, минусы и путь разработки)

Теория — это хорошо, но давайте посмотрим на цифры. Мы взяли реальный энтерпрайз-проект (**Signal-Android**, сотни файлов) и подготовили **10 реальных сценариев** разработки (Feature, Migration, Arch, Impact, Refactor, Info, Debug).

Мы стравили 5 агентов:
1. **Vanilla (rg)** — рипгреп и грубая сила.
2. **Naive Agent** — простой сборщик контекста без фильтрации.
3. **Graphify** — поиск графом вызовов по связям (NetworkX).
4. **AST-Index** — разрешение символов через tree-sitter, но без векторов.
5. **Наш Smart Agent** — production skill с RAG-демоном.

### Озарение: Two-Phase Blast Radius

Самая сложная задача — сценарий **Impact**: *«Что сломается, если я изменю базовый класс Job?»* Если просто искать `Job`, агент утонет в 500 файлах. Здесь работает алгоритм **Two-Phase Blast Radius**.

**Фаза 1:** просим систему (LSP + AST) вернуть определения и *все* использования. Получаем список из ~100 элементов.
**Фаза 2 (фильтрация):** читаем определения, запоминаем их директории, и из 100 использований оставляем только те, что:
1. находятся в той же директории, что и определение (приоритет 0 — ядро);
2. содержат имя символа в названии файла (приоритет 1 — скорее всего, реализация интерфейса);
3. входят в топ-10 по векторной близости (приоритет 2 — семантика).

Вместо чтения 50+ файлов агент получает ~15 **наиболее релевантных**.

### Результаты бенчмарка: цифры

| Агент | Ходов | Токенов | Precision | Coverage |
|-------|------:|--------:|----------:|---------:|
| **Smart Agent** | **~7** | **~3 800** | **73%** | **94%** |
| AST-Index | 13.9 | 16 400 | 23% | 73% |
| Graphify | 11.0 | 15 300 | 15% | 55% |
| Vanilla (rg) | 11.4 | 19 700 | 15% | 37% |
| Naive Agent | 38.0 | 13 900 | 7% | 94% |

- **Наивный агент** делает **38 ходов**, бесконечно читая файлы. Precision — 7%. Он находит почти всё (coverage 94%), но ценой чтения всего подряд.
- **Smart Agent** тратит ~7 ходов, потребляет в **4 раза меньше токенов**, а precision взлетает до **73%**.
- В сценарии **Refactor** (переименование интерфейса `SignalDatabaseMigration`) наш агент был *единственным*, кто нашёл все реализации; `ripgrep` дал 0%, потому что интерфейс имплементировался косвенно.

### Как ИИ планирует свои действия

Агент обращается к демону не текстом, а структурированным JSON. Для "push notification handler" встроенная LLM (Gemini Flash или Qwen) за миллисекунды генерирует план:

```json
{
  "queries": ["push notification", "notification handler", "FCM receiver"],
  "filters": {"language": "kotlin"},
  "strategy": "hybrid",
  "top_k": 20
}
```

Демон поддерживает несколько стратегий: `hybrid` (векторы + ключевые слова), `graph_walk` (шаги по графу вызовов), `global` (поиск по сводкам модулей). На выходе — готовый **Evidence Bundle**: релевантные файлы, извлечённые символы, граф вызовов и документация. Агенту больше не нужно искать — нужно только писать код.

## Как я доводил это до ума (история итераций)

С первого раза, разумеется, ничего не заработало. Честный путь разработки — с реальными цифрами из моих прогонов бенчмарка:

1. **Выпилил реранкер.** В исходной версии стоял cross-encoder реранкер (Qwen3-Reranker-4B через FastEmbed). Тяжёлая зависимость и латентность ради копеечного прироста. Удалил целиком — стало проще и быстрее.
2. **DI-aware чанкинг.** Наивная нарезка по AST теряла проводку Dependency Injection (а это именно то, что показывает, что с чем реально связано). Научил чанкер распознавать DI-паттерны.
3. **Two-Phase Blast Radius (главный шаг).** Сценарий «что сломается, если...» был худшим — тупой поиск возвращал 500 файлов. Двухфазный фильтр поднял precision на impact-сценариях с **5.8% → 17.6%**, сохранив 100% coverage.
4. **Структурная фильтрация использований + метаданные наследования.** Записал `inherits_from` в payload Qdrant и добавил проверки границ слова в AST-индексе, чтобы `Job` не матчился на `JobScheduler`. Результат: **−15% токенов на запрос без регрессии покрытия.**
5. **Persistent index-time LSP enrichment.** Запекаю данные о типах и вызовах от LSP в индекс один раз, вместо пересчёта. Именно это даёт zero-overhead в рантайме.
6. **FQN-based usage scroll + семантическая верификация.** Разрешаю использования по полному имени (FQN), затем семантически верифицирую кандидатов перед выдачей. Сценарий рефакторинга вышел на **50% precision при 100% coverage**.
7. **Compiler-verified call-graphs.** Текущая работа: заменяю эвристики «директория/имя» в ранжировании blast-radius на реальные рёбра графа вызовов от языкового сервера.

Каждый шаг гонялся через один и тот же бенчмарк из 10 сценариев — так было видно, какая правка какому типу задач помогла, а что регрессировало.

## Минусы RAG: за что вы платите

Я ничего не продаю, поэтому вот то, о чём обычно молчат в восторженных постах.

- **Индексация — это долго и тяжело.** Полная индексация Signal-Android заняла у меня **~5 часов** в первый раз (LSP-обогащение + 4096-мерные эмбеддинги на 300K+ строк — недёшево). Инкрементальная переиндексация быстрая, но холодный старт — реальное ожидание.
- **Диск тоже не бесплатный.** Для одного крупного репозитория: **1.1 ГБ кэш эмбеддингов + 747 МБ Qdrant + 224 МБ метаданных ≈ 2 ГБ.** 4096-мерные векторы точные, но толстые. Индексируете несколько больших проектов — закладывайтесь на объём.
- **Нужна работающая модель эмбеддингов.** Локально это Ollama + видеокарта (или терпение). Нет GPU — медленнее и индексация, и запросы.
- **Устаревание индекса — постоянный налог.** Векторы описывают код *на момент индексации*. File watcher тянет инкрементальные апдейты, но во время крупного рефакторинга индекс какое-то время «врёт» агенту. Вы поддерживаете второй источник правды.
- **Impact-анализ всё ещё слабый.** По типам задач: Feature/Arch/Info/Migration — **83–100% precision** (по сути решено), но **Impact / blast-radius («кто вызывает Recipient?») — ~19% precision.** Широко используемые символы (модель, к которой обращаются сотни файлов) раздувают множество кандидатов быстрее, чем эвристики успевают его подрезать. Двухфазный фильтр и работа над графом вызовов помогают, но проблему пока не закрыли.
- **Ещё одна практическая мелочь.** По логам запросов: точные символьные/ключевые запросы возвращаются за **150–300 мс**, а длинные расплывчатые запросы на естественном языке без языкового фильтра разлетаются по всему векторному пространству и могут занимать **10–19 секунд**. Давайте планировщику добавлять фильтры и предпочитайте конкретные формулировки.

## Выводы

RAG для кода превращает ИИ-агента из слепого котёнка в сеньора, который знает проект как свои пять пальцев. Вместо десятков ходов `grep` и чтения мегабайтов исходников агент делает точечные запросы к умному демону: экономит токены, спасает контекстное окно от мусора и работает быстрее.

Но это не магия. Вы платите ~5 часами на первую индексацию, парой гигабайт на диске и постоянной заботой об актуальности индекса. Импакт-анализ пока остаётся открытой проблемой. Для проектов на 100K+ строк, где агент регулярно теряется, этот размен для меня однозначно оправдан.

Проект не привязан к одному провайдеру: в `config.toml` можно выбрать `gemini`, `gpt-4o`, `claude` или поднять всё локально на `qwen3` через Ollama. Установка тривиальна: `pip install -e .` и запуск демона. Интеграция работает из коробки с Claude Code, Codex и Cursor.
